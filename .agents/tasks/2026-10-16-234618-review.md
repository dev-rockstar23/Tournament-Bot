# Razorpay payment integration for multi-tenant tournament platform

The implementation adds Razorpay payment processing to a multi-tenant tournament platform. Tournament organizers configure their own Razorpay credentials through an API endpoint. When players register for paid tournaments, the system creates Razorpay orders using the organizer's credentials, processes webhook notifications, and conditionally auto-approves registrations based on tournament settings.

**Watch for:** Missing `razorpay` npm dependency blocks TypeScript compilation (**confirmed**, HIGH). Webhook signature verification uses HMAC comparison on raw body, but the comparison function accepts any digest format without checking if the signature is hex-encoded (**confirmed**, MEDIUM). No admin UI exists for organizers to configure credentials (**confirmed**, MEDIUM). Amount passed to `createRazorpayOrder` is multiplied by 100 inside the function, but the API route passes a raw amount that may already be in paise (**likely**, MEDIUM).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The implementation creates a Razorpay order during payment creation by decrypting organizer credentials, calling the Razorpay SDK, and storing the returned `order.id` as `providerRef` in the database. Webhook events lookup orders by `providerRef` (the Razorpay order_id), verify HMAC signatures against the organizer's webhook secret, and update order status through a state machine. Auto-approval only fires when the tournament's `autoApprove` field is true and the payment status transitions to PAID. Credentials are encrypted at rest using AES-256-GCM with a 32-byte key from the environment. The payments package is missing the `razorpay` dependency in `node_modules`, causing TypeScript compilation to fail. No frontend UI exists for organizers to input credentials; only the API route is implemented.

1. **Missing razorpay dependency** — `razorpay` is declared in `package.json` but not installed. Run `pnpm install` in the workspace root to install it.
2. **Webhook signature comparison accepts non-hex input** — `verifyRazorpaySignature` converts the signature string to a Buffer using `'hex'` encoding but doesn't validate that the signature is actually hex. If Razorpay sends a different encoding or an attacker provides malformed input, the comparison may fail silently. Add a hex regex check before calling `Buffer.from(signature, 'hex')`.
3. **Amount unit ambiguity in createOrder API** — The `/orders` API route accepts an `amount` parameter without specifying units (paise or rupees). `createRazorpayOrder` multiplies by 100, assuming the input is in major currency units. If the caller passes paise, the order will be 100x the intended amount. Document the expected unit and add a validation check (e.g., reject amounts > 10000 INR to catch paise-unit mistakes).
4. **No admin UI for credential configuration** — The `POST /api/servers/:guildId/payment-config` endpoint is implemented, but no frontend page exists for organizers to input credentials. Add a page under `/servers/:guildId/admin/payment-config` or document that organizers must use curl/Postman.

If decryption fails, the webhook returns 500 instead of 400. Wrap decryption in a try-catch and return 400 with a clear error message.
6. **ENCRYPTION_KEY validation happens at runtime, not startup** — `getEncryptionKey()` throws if `ENCRYPTION_KEY` is missing or invalid, but this only happens when a credential is encrypted or decrypted. Add a startup check (e.g., in the web app's `middleware.ts` or a health check) to fail fast if the key is misconfigured.
7. **No test coverage for payment flow** — The review scope excluded running tests, but the payments package has no test files. Add tests for: encryption round-trip, HMAC verification with valid/invalid signatures, state machine transitions, webhook idempotency, and the full order creation + webhook flow.

## Razorpay order creation and providerRef storage

`createOrder` in `packages/payments/src/orders.ts` handles order creation for paid tournaments. After creating an order record with `status: PENDING`, it checks if the tournament's `entryType` is `'PAID'`. If so, it loads the tournament's `paymentConfig`, decrypts the `razorpayKeyId` and `razorpayKeySecret` fields, and calls `createRazorpayOrder` with the decrypted credentials. The function passes the internal order ID as `receiptId` to Razorpay.

```typescript
const razorpayOrder = await createRazorpayOrder({
  keyId,
  keySecret,
  amount,
  currency,
  receiptId: order.id,
})
```

`createRazorpayOrder` in `packages/payments/src/razorpay.ts` multiplies the amount by 100 before sending it to Razorpay:

```typescript
const amountInPaise = Math.round(amount * 100)
const order = await instance.orders.create({
  amount: amountInPaise,
  currency: currency.toUpperCase(),
  receipt: receiptId,
  payment_capture: 1,
})
```

This assumes the input `amount` is in major currency units (e.g., INR). The API route schema validates `amount: z.number().positive()` but doesn't specify units. If a caller mistakenly passes paise, the order will be 100x too large. The function returns the Razorpay `order.id`, which `createOrder` stores in the `providerRef` column.

The returned `razorpayCheckout` object includes the public `keyId` (safe to send to the client), the Razorpay `orderId`, and the `amount` (converted back to major units). This object is returned to the frontend to initialize the Razorpay checkout widget.

## Webhook event processing and order lookup by providerRef

The webhook route extracts `razorpayOrderId` from `payload.order.entity.id` and looks up the order by `providerRef` (the Razorpay order ID stored during order creation), not the internal database ID. It decrypts the tournament's `razorpayWebhookSecret` and passes it to `verifyRazorpaySignature`.

`processWebhookEvent` performs idempotency checking by querying `paymentEvent.providerEventId` (the Razorpay payment ID). If the event already exists, the function returns early. It verifies that the webhook's `amount` and `currency` match the stored order values, then maps event types to payment statuses (`payment.captured` → `PAID`).

## Auto-approve logic tied to tournament.autoApprove

After updating the order status to `PAID`, the webhook handler checks `order.registration.tournament.autoApprove`. If true, the registration status is set to `APPROVED`. If false, the registration remains `PENDING` after payment, requiring manual organizer approval. The logic is inside a transaction that also records the payment event and updates the order status.

## Credential encryption with AES-256-GCM

`encryptCredential` generates a random 16-byte IV, encrypts the plaintext with AES-256-GCM, retrieves the auth tag, and returns `{iv}:{authTag}:{ciphertext}` (all hex-encoded). `decryptCredential` splits the string, extracts the IV and auth tag, and decrypts the ciphertext. GCM mode provides authenticated encryption; if the auth tag verification fails, decryption throws (indicating tampering or corruption).

The encryption key is loaded from `process.env.ENCRYPTION_KEY` (must be 64 hex characters = 32 bytes). Key validation happens inside `getEncryptionKey()`, which is called on every encrypt/decrypt operation. If the key is missing or the wrong length, the function throws. This means misconfiguration is only detected at runtime when a credential operation is attempted, not at application startup.

## Webhook signature verification with timing-safe comparison

`verifyRazorpaySignature` computes an HMAC-SHA256 digest of the raw webhook body using the organizer's webhook secret and compares it to the signature from the `X-Razorpay-Signature` header using `timingSafeEqual`. The digest is computed as a Buffer, and the signature is converted from hex to a Buffer before comparison. The function doesn't validate that the signature string is hex-encoded before calling `Buffer.from(signature, 'hex')`. If the signature is malformed or uses a different encoding, `Buffer.from` will produce a buffer of the wrong length, causing the comparison to fail silently (length mismatch check returns false). Adding a hex regex check (`/^[0-9a-f]+$/i`) before conversion would reject malformed signatures explicitly.

The webhook route reads the raw body with `await req.text()` before parsing JSON, ensuring the signature is computed on the exact bytes Razorpay sent.

## Payment state machine transitions

The webhook handler calls `assertPaymentTransition(order.status, newStatus)` before updating the order. Allowed transitions:

- `PENDING` → `PAID`, `FAILED`, `EXPIRED`
- `PAID` → `DISPUTED`, `REFUNDED`
- `FAILED` → `REFUNDED`
- `DISPUTED` → `REFUNDED`
- `EXPIRED`, `REFUNDED` → (none)

The state machine prevents invalid transitions like `PAID` → `PENDING` or `EXPIRED` → `PAID`. `assertPaymentTransition` throws if the transition is invalid, causing the webhook handler to return 500.

## Payment configuration API with credential verification

`POST /api/servers/:guildId/payment-config` validates input with a Zod schema, then tests the credentials by creating a test order for INR 1. If the test fails, the endpoint returns 400. If successful, it encrypts all three credentials and upserts the `OrganizerPaymentConfig` record with `isVerified: true` and `isActive: true`.

The upsert uses a composite unique key `guildId_userId`, meaning each organizer can have one payment config per guild. The tournament's `paymentConfigId` foreign key references this config.

The `GET` endpoint decrypts the `razorpayKeyId` and masks it (first 4 characters + `'...'`). It returns `hasKeySecret: true` and `hasWebhookSecret: true` without exposing them.

## Missing razorpay npm dependency

The TypeScript compilation error shows the `razorpay` module is declared in `package.json` but not installed. Running `pnpm list razorpay` returns no output. The dependency must be installed before the code can compile.

## No admin UI for credential configuration

The API route `POST /api/servers/:guildId/payment-config` is implemented, but no corresponding frontend page exists. Searching for `razorpay` or `payment.*config` in `apps/web/src/**/*.tsx` returns no matches. Organizers have no way to configure Razorpay credentials through the web UI.
